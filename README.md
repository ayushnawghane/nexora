# Nexora

Nexora is the rebuild of Beacon's trusteeship ERP (the legacy `beacon-stack` / `stack-erp` app). It covers the full deal lifecycle for trustee products: lead → transaction → fees and schedule → engagement letter → approval → deal servicing → billing.

The legacy system is used as a **functional reference only**. Nexora is written from scratch, with a clean schema, strict validation and one consistent pattern for every module.

> **Status:** Phase 1 in progress (foundation + Debenture Trustee end-to-end). M0–M2 are complete and M3 (masters) is under way. See [Roadmap](#roadmap) and the detailed plan and progress in [`docs/PLAN.md`](docs/PLAN.md).

## Local setup (WAMP)

```bash
# 1. Install dependencies
composer install
npm install

# 2. Environment
cp .env.example .env
php artisan key:generate
```

3. Create the databases. Use utf8mb4 for both:
   ```sql
   CREATE DATABASE nexora CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   CREATE DATABASE nexora_testing CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   ```
4. Set the `DB_*` values in `.env`. The `LEGACY_DB_*` values only need to be correct if you'll run the legacy import; they point at a read-only copy of the old `beacon_stack` database.
5. Run migrations with the seeders, then build:
   ```bash
   php artisan migrate --seed
   npm run build
   ```
   The seeders load the permissions, the GST state codes and the Debenture Trustee product (`DEB`). In the `local` environment they also create a super-admin with employee code **`ADMIN`** and print a one-time temporary password in the console.
6. Serve the app. Either:
   - add a WAMP virtual host `nexora.test` pointing at `<project>/public`, or
   - run `php artisan serve` and open http://127.0.0.1:8000.
7. Sign in as `ADMIN`. The first sign-in asks you to set up 2FA with an authenticator app and then choose your own password.

### Running in development

On Windows, run these in separate terminals. Don't use `composer dev`: `pail` needs the `pcntl` extension, which isn't available on Windows.

```bash
npm run dev                 # Vite dev server with hot reload
php artisan serve           # skip if you use the WAMP vhost
php artisan queue:listen    # needed once mails/PDFs are queued
```

## Environment notes

- **`COMPANY_LOOKUP_DRIVER=fake`** keeps CIN/GST/PAN lookups offline. Switch to the real driver once UAT credentials (`CODIUM_API_*`) are available.
- **`MAIL_MAILER=log`**: outgoing mail, including approval links, is written to `storage/logs/laravel.log`.
- **Secrets never go in the repo.** Production and UAT values come from the server, not from git.
- **Timezone** defaults to `Asia/Kolkata` (`APP_TIMEZONE`).

## Engineering rules

These exist because of specific problems in the legacy app. Don't bend them.

- **Validate on both sides.** Every write endpoint has a FormRequest. The same rules are mirrored on the client so errors show inline as you type. A save never half-succeeds.
- **Let the database enforce correctness.** Use foreign keys, unique indexes, `NOT NULL` and enum/check constraints. Money is `decimal(18,2)`, never float. No comma-separated id columns; use pivot tables.
- **Strict models.** `Model::shouldBeStrict()` is on everywhere, so lazy loading and missing attributes throw.
- **Thin controllers.** FormRequest → Action class (`app/Actions/<Area>`) → Inertia response. Authorisation goes through policies/permissions, never hardcoded user, department or vertical ids.
- **Atomic writes.** Multi-table writes go in `DB::transaction`. Mail and other side effects run as queued jobs **after commit**.
- **No double submits.** Buttons disable while a request is pending, and create/issue actions are idempotent.
- **Page data comes as Inertia props.** Don't fetch on mount; use deferred props with skeletons for slow sections.
- **Links in emails** (e.g. approvals) are signed and expiring. GET requests never change state.
- **Every Action has a test.** Calculation logic (fee schedules, GST) has unit tests with real cases.
- **Eloquent only.** No `DB::table`, `DB::select`, `DB::raw`, `whereRaw` or other raw queries. Every model defines its relationships, and queries go through them. A test (`tests/Unit/Architecture/NoRawQueriesTest.php`) fails the build if raw queries appear. `DB::transaction` wrappers are fine.
- **Don't hand-build UI components.** Add components with the shadcn CLI (`npx shadcn@latest add <name>`). They land in `resources/js/Components/ui` and are themed by the tokens in `resources/css/app.css`. Only adjust generated classes where [`DESIGN.md`](DESIGN.md) asks for something specific. No one-off colours or ad-hoc styles.
- **Permissions live in one place.** Every permission is declared in `config/permissions.php`. A test fails if code references an undeclared one.

## Project structure

```
app/
  Actions/<Area>/          one class per use case (Auth, Users, …)
  Enums/                   states, fee types, frequencies (from M4)
  Http/Controllers/        thin controllers (Admin, Auth, Masters, …)
  Http/Middleware/         2FA, password freshness, recent-2FA for God Mode
  Http/Requests/           FormRequests for every write
  Models/                  Eloquent models with relationships
  Policies/
  Services/Auth/           TwoFactor (TOTP with replay protection)
  Support/Masters/         config-driven masters engine
  Support/Permissions.php  reads config/permissions.php
config/
  masters.php              definitions of the simple masters
  permissions.php          every permission, grouped for the role matrix
resources/
  css/app.css              DESIGN.md tokens mapped to shadcn variables (dark + light)
  js/Components/ui/        shadcn components (CLI-generated)
  js/Components/           compositions: sidebar, data table, combobox, confirm dialog, …
  js/Layouts/              AppLayout (sidebar shell), AuthLayout
  js/Pages/<Area>/         Inertia pages
  js/navigation.js         sidebar menu with route + permission per item
docs/
  PLAN.md                  Phase 1 plan and progress
  legacy-audit.md          full inventory of the legacy system
DESIGN.md                  design system (colours, type, components)
```

Later phases: the other products, billing and invoicing, ISIN, legal/security modules, outward and payouts, the client portals and reports.
